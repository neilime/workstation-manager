# Documentation rules

Keep documentation aligned with the implementation in every change.
[AGENTS.md](../../AGENTS.md) requires this review before completion.

## Audience and ownership

- Root readme files contain only focused end user documentation: purpose,
  prerequisites, everyday commands, and links into `docs/`. Put detailed usage,
  troubleshooting, architecture, CI, and testing in the appropriate guides.
- Put user procedures in `docs/usage/` and contributor instructions in
  `docs/development/`. Maintain [the documentation index](../README.md).
- Give each topic one canonical guide. Collection and role readmes contain a
  short purpose statement and links to details in `docs/`.
- Write concise, direct instructions: prerequisites, action, result, and any
  limitation that affects the user's decision. Keep implementation details in
  developer guides.

## Current behavior and history

Verify commands, options, defaults, configuration names, and guarantees against
the code and maintained configuration. Distinguish automatic work from manual
steps; describe only what setup, previews, backup, restore, and sync check.

Remove obsolete workflows, aliases, examples, compatibility notes, and migration
narratives. Do not keep them in active guides under a historical heading. Link to
maintained version pins and defaults instead of copying them into prose.

Preserve significant decision history in [ADRs](adr/README.md): context,
alternatives, decisions, consequences, and dated evidence. Accepted records may
describe former choices. Add a linked superseding ADR when a decision changes;
do not rewrite the accepted record to present old evidence as current validation.

## Generated documentation

GitHub Actions and workflow readme files are autogenerated. Do not hand-edit
them, including during a documentation cleanup. Update the source action or
workflow metadata, generator templates, or configuration, then use the existing
generation workflow and review the output. If that workflow is unavailable,
report the limitation instead of manually patching generated files.

Keep authored usage and contributor guidance in `docs/`. Links to generated
readme files must use their existing paths and anchors.

## Review each change

1. Verify affected commands, paths, defaults, ownership, and guarantees against
   the entrypoint, normalizers, owning role, or helper.
2. Update affected guides and examples in the same change. Check audience,
   remove duplicate or obsolete explanations, and preserve decision history in
   ADRs. Update every link, index, and anchor after moves; leave no compatibility stub.
3. Retain tests for current behavior. Remove retired scenarios and helpers;
   use synthetic inputs or maintained configuration instead of release snapshots.
4. Preserve tests for reruns, previews, permissions, credentials, recovery, and
   unmanaged data. Existing application state remains a valid safety fixture.
5. Regenerate affected generated docs from their sources. Run applicable lint,
   local file and heading-anchor checks, and affected tests. Documentation-only
   changes do not require workstation actions.
6. Report checks actually run and remaining limits. Keep acceptance requirements
   distinct from completed validation.

Shared personal instructions are maintained in the companion repository's
`home/dot_agents/` sources and installed by Chezmoi. Update those sources when
the same rule applies across repositories.
